# Meals, recipes and site owner tools

Food → Create meal / Create recipe opens a real ingredient builder. Choose one or several existing foods, adjust weights/volumes/portions or enter a label manually, and set the whole batch's serving count. Calculations preserve labelled energy; they do not substitute 4/4/9 energy. Manual nutrient values must be supplied, not invented. Up to 40 ingredients are supported. Micronutrients are included only when all ingredients supply them; ingredient estimate provenance remains attached and aggregated estimates stay labelled.

Save alone creates a reusable item. Save & add records the chosen servings in a diary group. Food → Saved meals & recipes reopens creations for editing. Stable IDs, immediate submit locks and owner-scoped version checks protect retries and concurrent edits. Diary entries retain independent ingredient snapshots. Editing a reusable recipe never changes previous diary entries. Existing legacy recipes/planning remain available under Recipes & meals; these are not migrated or removed by the new builder.

Owner setup uses three runtime secrets: FORM_OWNER_SETUP_EMAIL, FORM_OWNER_SETUP_TOKEN, FORM_OWNER_SETUP_EXPIRES. No owner email or token is embedded in frontend source. A one-time, expiring activation link supplies its token through a URL fragment, which is removed from browser history by the setup screen. The email is only an additional bootstrap eligibility check: a matching email alone grants no owner role. Explicit activation binds the authenticated stable account ID in site_owner; future authorization checks use this ID, not a profile name, profile email or email alias. A new account cannot take over by reusing the email. Changing ownership requires an authorized maintenance operation; no public reset endpoint is provided.

Connections → Feedback & updates / Site owner tools supports explicit feedback delivery, reporter-visible status, owner review, curated release announcements, reported-post hiding/restoration and rollout for five advanced-tool groups. Core logging and AI are not managed flags. Rollout controls are product visibility controls, not security permissions. Admin endpoints authorize independently on the server. Default rollout is on, and personal switches can still hide tools.

Social → Send report to owner requires explicit consent and access to the reported post. Only that post/caption/attachment and reason are forwarded. Earlier private reports are never exposed automatically. Owner report-photo access is scoped through an actual forwarded report. Hiding blocks feed, interaction and shared-media access without deleting original data; restoration is explicit. Owner action attempts are audited. Feedback and report details never become release notes automatically. Lists are bounded to 100 feedback/reports, 50 audit entries and 20 releases.

Validation: tests/food-creations-owner.mjs uses actual Miniflare D1/R2 and covers creation arithmetic, missing micronutrients, snapshot retention, account isolation, versions/retries, owner bootstrap, email impersonation rejection, feedback privacy, rollout cohorts, report consent, private-report exclusion and moderation enforcement. tests/food-creation-browser.mjs checks ingredient search, manual entry, portions, save/log, rapid clicks, library editing/history preservation and four viewport widths. tests/owner-tools-browser.mjs checks the explicit setup, fragment removal and real controls with controlled API fixtures. These do not certify a physical iPhone or grant role access before the owner activates their signed-in account.
